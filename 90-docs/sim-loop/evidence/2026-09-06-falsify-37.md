## 判定

### 主張 1 (帰属生存 + 増加継続) → **SURVIVED (帰属不変、増加継続)**
- main-refspec unused は 124 keys / 1.73 GiB へ**増加** (falsify-36 99 → +25 keys)。
- 同一時刻の resident-refspec unused = **0** — 増加後も 124 全件が resident 現在ツリー
  (data/ledger/) 参照のまま。falsify-25 の帰属は 124-key / 1.73 GiB スケールで**生存継続**。
- 増加源 itonami-app-resident.cljs (PID 94682) は同一 PID で稼働継続 — 帰属妥当。
- 増加レート継続 (falsify-36 +24 → 本 +25 keys / 反復)。

### 主張 2 (chunk drift 停止継続) → **SURVIVED (drift は停止のまま、間欠的)**
- chunk 数は falsify-36 の **14 → 14** で不変。tmp du も 178M / 14 ファイルで変化なし。
- falsify-35 の 1 chunk 解決 (15→14) 以降、連続 2 反復で drift なし —「drift は毎反復
  継続する単調現象」は引き続き REFUTED、間欠的である。

### 主張 3 (avail 大回復は増加源停止を反映) → **REFUTED (増加源は稼働継続のまま大回復)**
- avail は falsify-36 の 73Gi → **171Gi / 81%** へ +98Gi 大回復した一方、増加源
  itonami-app-resident.cljs PID 94682 は同一 PID で稼働継続を ps 実測 (etime 1日)。
- 「avail 回復 = 増加源の停止/減速」は falsify-30 に続き再反証 — 回復は増加源の停止に
  起因しない。171Gi は dropunused 直後 (falsify-32) と同等域で、劣化していた滞留容量
  (annex 参照) が何らかの経路で解放/未消費な状態へ戻ったと解釈されるが、単一起因の
  帰属 (どの容量が解放されたか) は本反復では特定不能 (falsify-34/35 の partially
  transferred は 14 個で不変、local annex は +25 増) — 継続観測対象。

総合: **falsify-25 の帰属は再蓄積 scale (124 keys / 1.73 GiB) で SURVIVED 継続**。

ingest) が存続する限り滞留の増加と再蓄積は続く。
