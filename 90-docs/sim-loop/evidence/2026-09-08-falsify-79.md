## 判定

**REFUTED (部分的不均一)** — 「4 コア全ての parity テストが host の実行実装へ結合し
checked replica として均一に機能する」は成立しない。実測で結合水準は 3 段に分かれる:

- **bot_slo latency / recovery**: parity テストは `#'…/latency-points` / `#'…/recovery-points`
  へ **live host fn を #' deref で機械結合** し、.kotoba guest と同一入力で比較 — host の
  decision 実装の drift を検出できる真の双実装 parity (checked replica として健在)。
- **bot_bounds**: parity テストの「host 側」は test ローカルに再記述した `host-code` cond
  (has-budget/spent/budget 3 スカラー) であり、実行中の `bot_bounds.cljc/admit-spend`
  ([b history] 入力、window / unreported を含む spent 計算) へ一切結合しない。もし
  将来 host の admitted boundary (`<` → `<=`) や spent/window 意味論が drift しても、この
  parity テストは .kotoba と test-local re-spec が一致し続ける限り PASS を返し続ける
  (drift 無検出、ドクストリングの「the host's rule」記述だけが現実と乖離する)。
- **bot_slo parts**: host に私有 fn が無い (evaluate に inline) ため host var へ結合不能を
  docstring 自認。.kotoba limbs をテスト内に再記述した公式に pin するのみ — host 側の
  evaluate の inline 数式が drift しても、専用 bot_slo_test は assembled stability を覆うため
  完全無検出ではないが、parts parity 自体は host 実装へ機械結合していない。

よって falsify-78 の「parity 付き checked replica (authority は host)」の blanket 記述のうち
parity の**結合質**は均一でなく、正確な範囲は「latency/recovery: live host var #' 結合の
checked replica / parts: host 結合なき guest-only formula pin / bounds: test-local re-spec との
み比較 (host 実装 drift を検出不能)」に精緻化される。score は **3 のまま** (質的反証 + 結合
水準の精緻化のみ。green 化測定は両 build-break 修理後のため不可、score 変動なし)。

## スコープ修正 / 次の 1 アクション

- **実装 軸の .kotoba 抽出評価に「parity 結合水準」を第 4 の次元として追記**: falsify-78 の
  (a) oracle 登録 (b) .kir.edn 配布 (c) host oracle/call に加え、(d) parity テストが
  **live host fn (#') へ結合しているか / test-local re-spec か / host 結合無しか** の 3 値を記録
  する方式を提案。bot_bounds は (d)=test-local re-spec、parts は (d)=host 結合なし、
  latency/recovery は (d)=live #' 結合。
- **Tier 2 report (kanban/human)**: bot_bounds の parity テストを「test-local host-code 再記述」から
  **live host fn 駆動へ張り替え** る修理案 — 例: `(#'bounds/admit-spend b hist)` を小さな adapter
  (map の :reason → 0/1/2 変換) で .kotoba の :i64 結果と等値比較するよう改め、host の
  admit-spend の境界 / spent / window 意味論が drift した時に parity が決定論的に赤くなるよう
  にする。実装は本体 checkout 編集 + テスト緑確認を要し Tier 1 不着地、kanban/human 判断。
  parts も同趣旨: evaluate の inline limbs を host 私有 fn へ抽出して #' 結合可能にすると
  host 側 drift も検出可 (Tier 2 提案)。
- build-break 修理 (falsify-68/75 の (B) identity.clj :import 復元 + (A) deps.edn kotoba-net 宣言)
  着地後に、上記 parity 結合の runtime 実行 (compile + テスト緑) を検証可能になる。
