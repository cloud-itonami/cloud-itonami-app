# falsify-23 (2026-09-06) — 「滞留世代は detached HEAD / manifest-rev 参照に保持され、参照解放で回収可能」説の反証試行

## 主張 (反証対象; falsify-22 の結論部)

cloud-itonami-dns-resolver の annex 滞留 3088 keys / 39.30 GiB は
detached HEAD (51d4010c) / manifest-rev の参照に保持されており、
manifest-rev 参照解放 (dead / branch 削除 / expire) を前提とすれば
回収可能である。

## 測定 (実測のみ)

対象: `~/github/com-junkawasaki/orgs/cloud-itonami/cloud-itonami-dns-resolver`

1. manifest-rev の参照実体 (falsify-22 の NEXT 測定):
   - `git rev-parse manifest-rev` = 51d4010c9410b25f0a8a0c25a9593a27c427cd32 (commit)
   - commit 51d4010c = `ingest: resident tick (--source tranco)` (2026-09-02 18:31:38 +0900)
   - reflog 実測: manifest-rev は `west update: moving to <sha>^{commit}`
     で更新される west (manifest ツール) 管理の branch。最終更新
     2026-09-03 14:32:56 +0900。更新主体は west update (本体側の
     manifest チェックアウト操作)。
2. manifest-rev と main の関係:
   - `git log --oneline manifest-rev..main` = 0 commits
     / `rev-list --count main..manifest-rev` = 352
   - `merge-base --is-ancestor main manifest-rev` = 真
   - つまり main ⊂ manifest-rev (manifest-rev は main より 352 commit 新しい)
3. manifest-rev と resident/dns-resolver の関係:
   - `merge-base --is-ancestor manifest-rev resident/dns-resolver` = 真
   - `rev-list --count manifest-rev..resident/dns-resolver` = 338
   - resident/dns-resolver 先端 eb427df5 (2026-09-06 11:40:52 ingest tick)
   - resident/dns-resolver は `/Users/junkawasaki/.gftd/worktrees/dns-resolver-resident`
     worktree で常時 commit 継続中 (ingest tick)

## 結論: REFUTED

「manifest-rev 参照解放で 3088 keys を回収できる」説は反証された:

- manifest-rev は resident/dns-resolver の祖先である。manifest-rev を
  解放 (branch 削除 / git-annex dead) しても、その 352 commit 分の
  履歴は resident/dns-resolver から到達可能なまま残り、annex 参照は
  解放されない (未達になるのは manifest-rev 先端から resident 分 338
  commit の差分のみ)。
- また main ⊂ manifest-rev なので、main だけでも滞留の大部分は
  保持される。falsify-22 の実測 (main/HEAD/manifest-rev で unused 集合
  が同一 3088 keys) と整合する。
- 滞留の真の参照元は「resident/dns-resolver branch が持つ 352+338
  commit 分の ingest 履歴」そのもの (ingest tick が生む annex key の
  過去世代全保持) であり、単一参照の解放で消える性質のものではない。
- 回収には resident branch 履歴の truncate / 履歴再構築 (ingest データの
  データロス判断を伴う) が前提となり、これは falsify-20/21 の
  「Tier 2: データロス判断」から更に一段重い (履歴改変) 判断である。
